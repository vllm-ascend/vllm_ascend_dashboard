# 精度看板架构调研

## 1. 结论

精度看板应作为“质量与模型”下的独立一级菜单，与“测试质量”“模型验证”“代码健康”并列，建议路由为 `/accuracy`。

它不是现有“模型验证”的一个 Tab：模型验证以模型配置、支持矩阵、报告归档和人工 Pass/Fail 为中心；精度看板以一次可追溯的评估运行、任务指标、统计变化和错误样本诊断为中心。二者共享模型身份和 CI 来源，但查询模型、数据粒度和生命周期不同。

现有 `model_reports` 可以继续作为兼容入口和原始报告归档，但不宜直接扩展成精度看板主表。推荐新增规范化的评估域表，并保留原始 JSON/对象存储引用，以同时满足列表聚合和样本下钻。

## 2. 参考页面的信息架构

调研对象：<https://ci.vllm.ai/eval>

页面采用两级主从结构。

### 2.1 一级：评估运行总览

1. 全局筛选
   - Model
   - Task
   - Image
2. 统计总览
   - Runs
   - Models
   - Tasks
   - Latest commit / time
   - Regression watch / improvements
3. 最强变化
   - task
   - model
   - 相比前次运行的百分点变化（pp）
   - 统计显著程度（σ）
4. 运行列表
   - when
   - commit / CI build link
   - image
   - model
   - task
   - score
   - stderr
   - n-shot
   - samples
   - eval duration
5. 分页

这里的核心对象不是 CI workflow 本身，而是“某次 CI 中某模型在某任务、某指标上的一次评估结果”。同一个 CI run 可以产生多条评估结果。

### 2.2 二级：单次评估样本下钻

点击运行行后打开详情面板，头部保留：

- task、model
- 主指标及 score/stderr
- n-shot、样本数
- CI build、commit、image、时间

样本区支持 All / Correct / Incorrect 分桶。样本摘要包含：

- correct/incorrect
- sample/doc index
- metric/filter（例如 `flexible-extract`、`strict-match`）
- extracted answer
- question 摘要

展开单样本后包含：

- question
- reference answer
- model response
- extracted answer
- metric result（例如 exact_match = 0）

页面当前只展示前 200 条样本；这说明样本数据必须独立分页或限流，不能随运行列表一次返回。

### 2.3 数据生产侧

vLLM 的 `perf-eval` 仓库以 workload recipe 组织一次 `(model, hardware, tasks)` 运行。recipe 同时描述 vLLM 服务、lm-eval 精度任务、性能任务及 BFCL；结果按 workload/task 输出后被看板摄取。

因此参考系统的逻辑链路是：

`workload recipe -> CI/Buildkite build -> result artifacts -> ingestion -> run/task metric -> sample detail -> dashboard`

## 3. 我们现有架构

### 3.1 前端组织

- React + TypeScript + Ant Design
- React Router 统一注册页面
- TanStack Query 管理服务端状态
- Axios service 封装 `/api/v1`
- “质量与模型”当前包含：测试质量、模型验证、代码健康

新增板块最自然的落点：

- 菜单：`质量与模型 / 精度看板`
- 路由：`/accuracy`
- 页面：`frontend/src/pages/AccuracyDashboard.tsx`
- service：`frontend/src/services/accuracy.ts`
- types：`frontend/src/types/accuracy.ts`

不建议放进 `/models` 的 Tabs。精度看板要同时横向筛选多个模型，模型详情页则以单个 `model_id` 为上下文。

### 3.2 后端组织

- FastAPI 路由统一挂到 `/api/v1`
- SQLAlchemy async + MySQL
- scheduler 产生采集任务，collector executor 执行
- GitHub client 获取 workflow runs 和 artifacts
- parser 将 artifact 转为领域数据
- contracts/schemas 定义 API DTO

推荐新增独立领域边界：

```text
backend/
  accuracy/
    service.py
    ingestion.py
    regression.py
  tooling/parsers/
    lm_eval_parser.py
  contracts/schemas/
    accuracy.py
  api/v1/
    accuracy.py
```

### 3.3 现有模型报告链路

当前链路为：

`model_sync_configs -> GitHub workflow runs -> artifact ZIP -> ModelReportParser -> model_reports`

已有能力：

- 按 workflow、branch、artifact pattern 配置同步
- 解析 YAML/JSON
- 兼容 lm-eval `results` 聚合格式
- 将 task metrics 扁平化到 `metrics_json`
- 保存 `tasks` 和 `report_json`
- 基于同一模型的两份报告做简单差值对比

### 3.4 当前数据模型的缺口

`model_reports` 目前主要字段是 `model_config_id`、`workflow_run_id`、`report_json`、`metrics_json`、`tasks`、版本、硬件及 Pass/Fail。它存在以下限制：

1. task/metric 存在 JSON 内，无法高效完成跨模型、跨任务的筛选、排序和分页。
2. 没有显式保存 `stderr`、样本数、few-shot、eval duration、主指标名。
3. 没有显式保存 image、commit/build URL、artifact 身份和采集状态。
4. 没有样本级实体，无法查询错误样本及保存 question/reference/response/extracted answer。
5. lm-eval 旧格式被默认判为 pass，不能替代“相对前次运行的统计回归”判断。
6. 同步去重只检查 `workflow_run_id`；一次 workflow 有多个模型/任务/artifact 时粒度过粗，部分成功后的重试也可能跳过未摄取结果。
7. 每个 artifact 只读取第一个匹配文件，无法同时摄取聚合结果文件和 samples 文件。
8. 模型身份仍处于 `model_configs` 与 `model_registry` 双轨过渡期。

`test_cases/test_runs` 也不适合复用：它们描述 pytest/JUnit 用例执行、flaky 和失败分类；lm-eval 样本是 benchmark document/response，身份和统计语义不同。

## 4. 推荐数据架构

### 4.1 领域关系

```text
CIResult / external build
        1
        |
        n
accuracy_eval_runs
        1
        |
        n
accuracy_eval_results ---- n:1 ---- model_registry
        1
        |
        n
accuracy_eval_samples
```

为减少首期表数量，也可以把 run 和 result 合并；但考虑一个 build/workload 可包含多个 tasks/metrics，长期推荐分层。

### 4.2 `accuracy_eval_runs`

一次可追溯的评估执行/工作负载。

建议字段：

- `id`
- `source`：github_actions/buildkite/manual
- `source_run_id`、`source_job_id`、`source_build_number`
- `source_url`
- `workflow_name`、`workload_name`
- `commit_sha`、`branch`
- `image`
- `hardware`、`device_count`
- `vllm_version`、`vllm_ascend_version`
- `started_at`、`completed_at`、`duration_seconds`
- `artifact_id`、`artifact_name`、`artifact_digest`
- `ingestion_status`、`ingestion_error`
- `raw_metadata` JSON
- `created_at`、`updated_at`

唯一键建议为 `(source, source_run_id, artifact_id, workload_name)`，不能只用 workflow run ID。

### 4.3 `accuracy_eval_results`

一条可进入排行榜和趋势计算的 task/metric 结果。

建议字段：

- `id`
- `eval_run_id` FK
- `model_registry_id` FK（过渡期可再带 `model_config_id`）
- `model_name_snapshot`
- `task_name`
- `metric_name`（如 `exact_match`）
- `metric_filter`（如 `flexible-extract`）
- `score`
- `stderr`
- `num_fewshot`
- `sample_count`
- `eval_duration_seconds`
- `higher_is_better`
- `previous_result_id`
- `delta_absolute`、`delta_pp`
- `sigma_change`
- `change_status`：regression/improvement/stable/insufficient_data
- `raw_result` JSON
- `created_at`

唯一键建议为 `(eval_run_id, model_registry_id, task_name, metric_name, metric_filter)`。

主要索引：

- `(task_name, model_registry_id, created_at)`：找同序列前次结果
- `(model_registry_id, created_at)`
- `(change_status, created_at)`
- `(commit_sha)` 可通过 run 表关联

### 4.4 `accuracy_eval_samples`

样本详情表必须与聚合结果分离。

建议字段：

- `id`
- `eval_result_id` FK
- `doc_id` / `sample_index`
- `repeat_index` 或稳定的 `source_sample_key`
- `metric_name`、`metric_filter`
- `is_correct`
- `question` LONGTEXT
- `reference_answer` LONGTEXT
- `model_response` LONGTEXT
- `extracted_answer` LONGTEXT
- `score`
- `prompt_hash`、`doc_hash`、`target_hash`
- `raw_sample` JSON/LONGTEXT
- `created_at`

不能以 `(result_id, sample_index)` 单独做唯一键：lm-eval 同一 doc 可能有多个 repeat、metric/filter 结果。

主要索引：

- `(eval_result_id, is_correct, sample_index)`
- `(eval_result_id, metric_filter, is_correct)`

如果样本规模快速增长，首期可在 MySQL 保存可检索摘要与对象存储 URI，完整 raw sample 放压缩 JSONL；但用户点击详情需要的 question/reference/response 最好仍能按单条快速读取。

### 4.5 原始数据与规范化数据

采用“双层保存”：

- 原始层：保留完整 artifact 元数据和原始 JSON，便于追溯、重新解析和兼容 lm-eval 格式变化。
- 查询层：把 run、task metric、sample 的核心字段规范化，支撑索引、筛选、分页和回归计算。

不要只存 JSON，也不要只存拆表后的字段。

## 5. 推荐 API

```text
GET /api/v1/accuracy/filters
GET /api/v1/accuracy/overview
GET /api/v1/accuracy/results
GET /api/v1/accuracy/results/{result_id}
GET /api/v1/accuracy/results/{result_id}/samples
GET /api/v1/accuracy/results/{result_id}/samples/{sample_id}
GET /api/v1/accuracy/trends
POST /api/v1/accuracy/sync            # 管理员/任务入口
```

关键约束：

- `results` 服务端分页，并支持 model/task/image/commit/hardware/date/change_status。
- `samples` 服务端分页，并支持 all/correct/incorrect 和 metric_filter。
- `overview` 与当前筛选条件一致，不能返回全局总数造成口径不一致。
- 默认主指标必须由 task 配置决定，不能假设所有任务都是 exact_match。

## 6. 回归检测口径

参考页面同时展示 `delta pp` 与 `σ`，但仅从 UI 无法确认它的精确公式。我们不应复制一个未经确认的阈值。

建议首期规则：

1. 只在相同 model + task + metric + filter + 可比运行环境内比较。
2. 基线默认取上一次成功完成且样本量有效的结果。
3. `delta_pp = (current_score - baseline_score) * 100`。
4. 若两次均有 stderr，可计算合并标准误：
   `sigma_change = abs(delta) / sqrt(stderr_current^2 + stderr_baseline^2)`。
5. 状态阈值配置化，例如同时满足 `delta_pp <= -1` 且 `sigma_change >= 2` 才标记 regression。
6. image/hardware/device_count/num_fewshot 等关键条件不一致时标为 `insufficient_data`，而不是直接比较。

阈值应放到独立配置，不复用 `ModelConfig.pass_threshold`；后者是绝对门槛，回归检测是相对门槛。

## 7. 推荐采集链路

```text
scheduler
  -> collection task: accuracy_sync
  -> GitHub Actions artifact / 外部评估 artifact
  -> lm_eval parser
  -> upsert eval_run
  -> upsert task/metric results
  -> 批量导入 samples
  -> 计算 previous/delta/sigma/change_status
  -> 提交事务并记录摄取状态
```

实现原则：

- 聚合结果与 samples 文件要分别识别，不能“第一个匹配文件即结束”。
- 以 artifact digest + 细粒度业务键实现幂等。
- 单个 artifact 失败不能让整个 workflow 永久被判定为已同步。
- samples 使用批量 insert/upsert，避免逐条 commit。
- 先导入 run/result，samples 可异步补齐；前端显示 `samples_pending` 状态。
- 通过正式迁移脚本建表，不在生产库直接改表。

## 8. 与现有模块的边界

| 模块 | 关注对象 | 精度看板的关系 |
|---|---|---|
| 测试质量 | pytest/JUnit 用例、稳定性、flaky、责任人 | 不复用用例/运行表，只共享 CI 溯源 |
| 模型验证 | 模型配置、支持矩阵、报告、人工 Pass/Fail | 共享模型身份；可从模型详情跳转到已筛选精度结果 |
| 精度看板 | benchmark task/metric、统计回归、样本答案 | 新领域表和 API |
| CI 运行 | workflow/job 状态与日志 | 通过 run/job ID 和 commit 建立追溯链接 |

## 9. 分阶段范围

### MVP

- 独立菜单与路由
- model/task/image 筛选
- 总览卡片、回归列表、评估结果分页表
- 单结果正确/错误样本分页与详情
- GitHub Actions artifact 摄取
- 基于上一次可比结果的 delta/stderr 显著性计算

### 后续

- 多结果趋势图与版本对比
- 精度与性能联合分析
- 按 release/branch/hardware 的基线策略
- 回归告警接入现有告警规则
- BFCL、生成式 judge、pass@k 等非二元样本结果

## 10. 实施前必须确认的输入

1. vLLM Ascend 当前精度 CI 的 workflow 文件名和 artifact 命名规则。
2. artifact 内实际 lm-eval 版本、聚合结果文件和 samples 文件样例。
3. image、硬件、device count、commit 的权威来源。
4. 首批任务及每个任务的主指标/方向。
5. 回归告警阈值与可比环境规则。
6. 样本保留周期及是否允许保存完整 prompt/response。

在拿到一份真实 artifact 前，可以完成页面骨架、API contract 和迁移设计，但不应锁死 parser 与回归口径。
